# followup mode

You are in **followup** mode: work the open follow-up blocks a previous run left in its working doc (`core.md`), with the user's decisions, review-first. No argument is needed — resolve the doc from the repo. An optional argument names an older run doc explicitly, or filters the blocks by area/path.

This mode runs the **build** workflow (`build.md`) for every approved item — its gates govern the dev cycle; the sections below specialize intake and shipping. It is attended: every block exists precisely because it needs a human decision, so nothing ships without one.

**followup does not open a working doc of its own.** The source doc is the working doc: statuses are updated there, and findings discovered during the follow-up work are appended there. One run, one doc, however many follow-up passes it takes to drain.

## Intake

1. **Resolve the doc.** Glob `/tmp/tokenmaxxer-<repo-basename>-*.md` and pick the most recently modified one **that has `open` or `deferred` blocks** — not simply the newest, which is often a later run that left none and would shadow an older doc still holding work. Report which you picked, how many open blocks it has, and how many other docs also have open blocks, so a wrong pick costs one word to correct. An explicit argument overrides the pick. Only when *no* doc has open or deferred blocks: say there is nothing to follow up and stop. Work one doc per invocation — never merge two docs' blocks into one batch.
2. **Re-verify before asking.** Evidence goes stale: PRs merge, code moves. Check each block against the current default branch — confirm the defect still exists at (or near) the recorded location, holding the evidence to the standards in `triage.md` (evidence priority; no invented ground truth). A block that no longer reproduces is marked `declined (resolved elsewhere)` with one line of evidence; never bring a dead item to the user. An operational leftover is re-verified against its branch, not against a code location.
3. **Decisions first, execution second.** Present the surviving blocks grouped by subsystem and ordered by `tier`, worst first. Give each as its recorded decision question plus recommendation. Offer **fix / skip / defer** when the block carries an established mechanism, and **investigate / skip / defer** when it does not — the block's own evidence decides which, never the user, so nobody is offered a fix that would have to invent a mechanism. If the user picks *fix* on a block with no mechanism, run *investigate* first and return with the mechanism before implementing. Collect the whole batch before implementing anything, so a long session never splits a decision from its context.

## Execution

- Each *fix* item is a build-workflow task seeded by its block: the evidence is the triage (established when the block was recorded and re-verified at intake — do not re-investigate a proven mechanism), and the user's answer is the approval of intent. Build's trivial fast path applies on build's own criteria; the external diff gate is never skipped.
- An *investigate* item is one whose mechanism was never established — a block recording a root cause still unresolved after triage, or a question like "which behavior did you intend here". Run `triage.md` (or `skill: investigate`) first, then bring the established mechanism back to the user as a fix decision. Never implement one as if its mechanism were proven; that is the pretence the block exists to prevent.
- An item that is really an accreted-component consolidation is not absorbed here: recommend a `refactor <component>` run and mark the block `deferred` to it.
- An *Incomplete* leftover (a verified branch whose push or PR-creation failed, with its recorded command and error): confirm with the user, then finish the recorded step and whatever remains of the shipping sequence it stalled in — a retried push that succeeds still needs its draft PR opened. Never re-implement work that already passed its gates. Close it `done` only when the whole stalled sequence completes — `done (<PR>)` when a PR results, `done (<the step that was completed>)` when the sequence legitimately ends without one. If a later step fails in turn (the push lands, the PR create then fails), the block stays `open` with its recorded command and error updated to the new failure point; never close on partial progress.
- Ship per subsystem: approved items touching one subsystem ride one branch → one draft PR, each item its own commit, its `sweep-key` line in the PR body — so CI runs once per subsystem and the next sweep's dedup suppresses everything handled here. This explicitly overrides build's implementation steps 1 and 9: the subsystem branch, cut once from the fresh default branch, replaces the per-item branch, and the PR opens once per subsystem after its last item's gates pass — never per item.

## Close the loop

Update each block's status in the source doc in the same run: `done (PR)` for shipped items, `declined (reason)` for skips, `deferred` for the rest. Out-of-scope findings discovered *during* follow-up work are appended to the same doc as new `open` blocks per `core.md` — follow-ups spawn follow-ups; the doc after the run is the queue for the next pass.
